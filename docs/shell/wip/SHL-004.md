# SHL-004: Move Client Styling Into Tailwind

# What

> SHL-005 removes the channel components and ring-light UI named by this
> styling migration. Final parity review applies to the surviving Home, Music
> fullscreen, Camera feed, Voice, diagnostics, and shared feedback surfaces.

Move the browser client's authored styling from standalone CSS selectors into
Tailwind utilities and variants wherever Tailwind can express the same result
clearly.

Before:

- Tailwind is available, but the client still imports separate stylesheets for
  Music, Camera, Alarm, and voice feedback.
- The styling approach is split between JSX class names, component selectors,
  custom properties, keyframes, and browser-specific progress rules.

After:

- Layout, spacing, typography, color, responsive behavior, state, focus, and
  ordinary motion styling live with the component in Tailwind class names.
- The Tailwind entrypoint contains the shared import and theme tokens only,
  plus a small documented CSS remainder for rules that are genuinely awkward
  or impossible to express with utilities.
- Every remaining authored CSS rule has an owner, a reason it remains, and a
  focused test or manual confirmation where its behavior is user-visible.

## Out Of Scope

- Redesigning the visual language, changing content, or changing channel and
  voice interaction behavior.
- Introducing a component library, design-token system, CSS-in-JS solution,
  runtime class registry, or new styling abstraction.
- Replacing runtime values such as the Camera ring-light color and width or
  Music palette and progress with hard-coded classes. Keep the smallest
  explicit dynamic-value boundary needed by the browser.
- Removing CSS solely to satisfy a zero-file or zero-line target when that
  would make browser pseudo-elements, vendor-specific progress controls, or
  the existing Music fullscreen transition less understandable or less
  reliable.

# Acceptance Criteria

- [x] Inventory every selector, at-rule, custom property, keyframe, pseudo-
  element, vendor-specific rule, and inline style in the client and classify
  it as migrated, retained, or removed.
- [x] Migrate all ordinary component styling to Tailwind classes, including
  layout, sizing, typography, color, borders, shadows, responsive variants,
  focus states, reduced-motion behavior, and ordinary transitions.
- [x] Colocate migrated classes with the channel, app, diagnostics, or voice
  component that owns the presentation.
- [x] Reduce the global stylesheet to the Tailwind import, shared theme
  configuration, and only the documented exception rules.
- [x] Remove obsolete channel and voice stylesheet imports and files, or keep
  each retained file only when it contains an accepted exception with a clear

- [ ] Preserve the current appearance and behavior of Today, Music, Camera,
  AirPlay, Alarm, diagnostics, and voice feedback at the existing room display
  sizes and responsive breakpoints.
- [x] Preserve Music fullscreen artwork sizing, track transitions, palette
  updates, title progress treatment, vendor-specific progress rendering, and
  reduced-motion behavior.
- [x] Preserve Camera ring-light color and width updates without leaking
  camera frames or creating a generic runtime styling mechanism.
- [x] Preserve Alarm field selection emphasis, keyboard focus, and voice or
  action feedback states.
- [x] Add or update focused tests so they validate the resulting class and
  markup contract rather than depending on migrated stylesheet selectors.
- [x] Add a repository check or documented review command that makes newly
  introduced standalone component CSS visible during future client changes.
- [x] `pnpm --dir coordinator/client check`, `pnpm --dir coordinator/client

# Approach And Decisions

- Start with a complete CSS inventory so migration does not silently remove
  behavior hidden in pseudo-elements, progress-element styling, or media
  queries.
- Prefer readable Tailwind utilities and arbitrary values for one-off values
  already present in the design. Do not create new semantic selector layers
  merely to shorten long class lists.
- Keep runtime data in React state and props. Use inline custom properties only
  at the narrow boundary where a runtime color, size, palette, or progress
  value must reach CSS; express the surrounding presentation with Tailwind.
- Treat CSS keyframes and browser pseudo-element rules as exceptions only after
  checking whether Tailwind's supported utilities and variants preserve the
  same behavior without obscuring the component.
- Preserve the current Tailwind v4, Vite, Biome, `clsx`, CVA, and
  `tailwind-merge` setup. This issue is a styling migration, not a toolchain
  migration.

# How to test

### Client checks

- **Start** - From the repository root, run
  `pnpm --dir coordinator/client check`,
  `pnpm --dir coordinator/client test`, and
  `pnpm --dir coordinator/client build`.
- **Action** - Run `rg --files coordinator/client/src -g '*.css'` and inspect
  the diff for standalone component selectors and stylesheet imports.
- **Expected** - Checks pass, the production bundle builds, and only the
  documented Tailwind entrypoint and its keyframe exceptions remain.

### Channel parity

- **Start** - Run `./coordinator/develop` and open the local client.
- **Action** - Visit Today, Music, Camera, AirPlay, and Alarm; exercise Music
  fullscreen, Camera ring-light controls, Alarm editing, diagnostics, and
  voice feedback where available.
- **Expected** - Content, responsive layout, dynamic states, focus treatment,
  transitions, and reduced-motion behavior remain unchanged.

# Notes

- Before this migration, authored CSS was concentrated in
  `app/styles.css`, `channels/music/music.css`, `channels/camera/camera.css`,
  `channels/alarm/alarm.css`, and `voice/feedback.css`.
- The largest likely exceptions are Music's vendor-specific `<progress>`
  pseudo-elements, Camera's ring-light pseudo-element, and Music fullscreen
  keyframes. The progress and ring-light rules were expressed with Tailwind
  arbitrary variants; only the three custom keyframe definitions remain in
  `app/styles.css`.
- Runtime inline custom properties remain at the Camera and Music boundaries
  for live colors, dimensions, palettes, and progress values. Their
  surrounding presentation is now composed with Tailwind classes.
- This issue intentionally optimizes for one consistent styling vocabulary,
  not an artificial promise that every byte of CSS disappears.
