## Implementation Walkthrough

### 1. Qualify The Receiver Package

The iMac is an `amd64` Ubuntu 24.04 endpoint. We downloaded the upstream
architecture-specific Raspotify package, inspected its Debian metadata, and
accepted one exact version and SHA-256 checksum. The committed host installer
repeats those checks before `apt-get` can install the package:

```text
endpoint/imac/provision-raspotify-host
```

It rejects a changed package name, version, architecture, checksum, or an
Ubuntu build that does not depend on `libasound2t64`. Updating Raspotify later
therefore requires deliberately reviewing and changing both the pinned version
and checksum in that script.

### 2. Share The Existing Audio Session

The packaged service normally uses direct ALSA. Cortex Home instead installs
three fixed files:

```text
endpoint/imac/files/raspotify.conf
endpoint/imac/files/raspotify.service.conf
endpoint/imac/files/cortex-raspotify
```

The configuration names the receiver `Cortex Home` and selects PulseAudio. The
systemd override runs it as `cortex-endpoint`, after LightDM, while the wrapper
waits up to 30 seconds for that user's PulseAudio socket before starting
librespot. Spotify and Chromium can then share the already qualified analog
route to the Sonos instead of competing for ALSA.

### 3. Provision Or Restore Raspotify

A complete endpoint rebuild includes Raspotify through the normal entry point:

```sh
./endpoint/imac/provision
```

On an already provisioned endpoint, install or restore only the receiver:

```sh
./endpoint/imac/provision-raspotify
```

Both commands copy a fixed snapshot to a validated temporary directory on the
iMac and run the same root-owned host installer. The focused command asks only
for the existing `imac` account's sudo password. Spotify credentials are not
stored in the repository or required by the provisioning command because
pairing uses Spotify Connect discovery.

### 4. Verify The Rebuilt Receiver

After provisioning, verify unattended service state from the ThinkPad:

```sh
ssh imac 'systemctl is-enabled raspotify.service'
ssh imac 'systemctl is-active raspotify.service'
ssh imac 'systemctl cat raspotify.service'
```

The first two commands should print `enabled` and `active`. The effective unit
should show the `50-cortex-endpoint.conf` drop-in, `User=cortex-endpoint`, and
the `/usr/local/bin/cortex-raspotify` entry point.

Open Spotify on the iPhone, select a normal album or playlist track, and choose
`Cortex Home` from the available devices. The track should become active in
Spotify and play through the Sonos line-in. This manual check proves discovery,
provider playback, the PulseAudio route, the analog output, and the Sonos input
together.

## Problems Encountered

### 1. Destination Directories Did Not Exist

- Symptom: The first deployment required manually creating `/etc/raspotify`
  and `/etc/systemd/system/raspotify.service.d`.
- Diagnosis: The initial copy assumed both package and systemd configuration
  directories already existed on a fresh endpoint.
- Resolution: `provision-raspotify-host` now uses `install -D` for the
  configuration and drop-in, creating their parent directories with the
  intended ownership and modes.
- Remaining caveat: The corrected focused provisioner still has an unchecked
  reviewer rerun, so this record does not claim that interaction was observed.

### 2. Apt Asked Which Configuration To Keep

- Symptom: Package installation stopped at an interactive `/etc/raspotify/conf`
  conffile question.
- Diagnosis: Cortex Home installed its reviewed configuration before `apt`
  installed the package that owns the same path.
- Resolution: The initial install was completed by keeping the existing file.
  The host installer now passes `Dpkg::Options::=--force-confold`, so reruns
  retain the repository-owned configuration without an interactive prompt.
- Remaining caveat: A future package that changes its configuration contract
  must be reviewed alongside the pinned version and checksum.

### 3. Spotify Appeared To Play Without Sound

- Symptom: The iPhone could select `Cortex Home` and showed playback, but the
  Sonos initially remained silent.
- Diagnosis: The packaged service defaults to its own direct ALSA context,
  while the qualified endpoint route belongs to the logged-in
  `cortex-endpoint` PulseAudio session used by Chromium.
- Resolution: The systemd drop-in runs Raspotify as `cortex-endpoint`; the
  wrapper waits for and exports that user's PulseAudio socket; and the
  Raspotify configuration selects the PulseAudio backend. A normal track then
  opened the same running analog PCM and played through the Sonos.
- Remaining caveat: Raspotify depends on the unattended endpoint session
  successfully starting its PulseAudio server.

### 4. A Station Context Failed Before Audio Opened

- Symptom: The first station or autoplay selection produced librespot context
  errors and no sound.
- Diagnosis: The provider context failed before librespot opened the
  PulseAudio sink, so it was not evidence of another audio-route failure.
- Resolution: Testing with a normal album or playlist track immediately used
  the active analog PCM and produced audio. The manual procedure now starts
  with that predictable context.
- Remaining caveat: Unsupported or changing Spotify contexts may still fail
  independently of Cortex Home's local audio path.

### 5. Playback Was Quieter Than Expected

- Symptom: Working Spotify playback through the Sonos was noticeably quiet.
- Diagnosis: The saved iMac Master and Headphone controls were each at 70%,
  represented by ALSA as -19 dB, before Sonos line-in source level and room
  volume were applied.
- Resolution: No gain change was committed because preferred listening level
  is a reviewer judgment. The relevant controls can be inspected and adjusted
  on the iMac with:

  ```sh
  sudo amixer -c 0 sset Master 100% unmute
  sudo amixer -c 0 sset Headphone 100% unmute
  sudo alsactl store 0
  ```

- Remaining caveat: Those values are suggested line-level starting points, not
  confirmed settings. Tune them together with Sonos line-in source level, room
  volume, and the identify signal before making them permanent.

## Heatmap

## Hot

### H1 - Share The Endpoint PulseAudio Session

- Decision: Run the packaged librespot receiver as `cortex-endpoint` through
  that user's PulseAudio server.
- Where: `endpoint/imac/files/raspotify.service.conf` and
  `endpoint/imac/files/cortex-raspotify`.
- Why: Chromium already owns this sound-server route. Sharing it avoids direct
  ALSA contention and does not add a system audio server.
- Alternatives: Direct ALSA; a system PulseAudio daemon; network audio from the
  ThinkPad.

### H2 - Fail When The Reviewed Package Changes

- Decision: Pin the accepted package metadata and checksum while downloading
  through the upstream architecture-specific URL.
- Where: `endpoint/imac/provision-raspotify-host`.
- Why: A changing `latest` package must not silently alter dependencies,
  service hardening, or receiver behavior during endpoint reprovisioning.
- Alternatives: Trust the latest package; add the upstream apt repository;
  build librespot locally.

## Warm

- What: The focused installer and full endpoint provisioner share one

- What: Credentials and audio caching remain disabled; zero-conf pairing does

  unsuccessful station attempt never opened the PulseAudio sink, while a
