# LGT-001: Connect The Hue Bridge

Previous identifier: `GH-008`.

## What

- Added pinned `aiohue==4.8.1` to an isolated coordinator Python environment
  without adding Home Assistant or raw Hue protocol code.
- Added one explicit pairing command that validates a locally supplied bridge,
  requires its physical link button, stores the generated credential outside
  the repository, and reports only sanitized capabilities.
- Added one coordinator-owned Hue adapter with bounded startup, shutdown,
  retry, authentication, and V2 event-connection state.
- Added safe Hue operational state to coordinator health without exposing
  bridge identity, credentials, resource IDs, lighting state, or actions.
- Kept scenes, remote mappings, lamps, the Hue app, and existing manual control
  bridge-owned and unchanged.

## Plan Diff

- `aiohue` provides local bridge validation for a supplied host, while its
  automatic N-UPnP discovery calls a Philips cloud service. The operator
  command therefore takes `<bridge-host>` at runtime and validates that bridge
  locally instead of adding another discovery dependency or using the cloud.
- Pairing reports the V2 bridge's advertised remote event values and includes
  one fixed 60-second sanitized event observation window. This keeps hardware
  qualification in the existing one-time command instead of adding a
  diagnostic service or raw-event logging.
- Malformed or identity-mismatched host configuration has the additional
  `invalid_configuration` health state so it cannot be confused with bridge
  reachability.

## Implementation Walkthrough

### 1. Build One Isolated Runtime

`coordinator/requirements.txt` contains the single direct pin
`aiohue==4.8.1`. The stable deployment entry point remains:

```sh
./coordinator/install <server-ssh-host>
```

It builds the unchanged React client and copies the coordinator, Hue module,
pairing program, service unit, and dependency declaration to the server.
`coordinator/install-host` requires Python 3.11 or later with `venv` support,
recreates `/opt/cortex-home/venv`, installs the pin, runs `pip check`, and
starts the service with that environment. Node and pnpm remain build-time only.

The installer preserves `/etc/cortex-home`; ordinary deployment does not
remove or replace an existing Hue credential.

### 2. Pair Deliberately And Store One Host Secret

Deploy before the first pairing, then run:

```sh
./coordinator/pair-hue <server-ssh-host> <bridge-host>
```

The wrapper accepts only an IPv4 address or local hostname, connects through
the existing SSH path, and runs `coordinator/hue_pair.py` as root. The program
validates the supplied host as a Hue bridge over the LAN, waits for the
operator to press the physical bridge link button, and asks `aiohue` to create
the application key.

The program creates `/etc/cortex-home/hue.json` exactly once, owned by
`root:cortex-home` with mode `0640` under a `0750` directory. It prints a
success message and sanitized room, scene, remote model, control, and
advertised-event information, never the application key, bridge ID, network
host, or raw resource IDs. The wrapper restarts the coordinator only after
pairing exits successfully.

Pairing then observes sanitized remote button events for at most 60 seconds.
Use every short, repeated, and held press intended for later channel mapping
during this window.

### 3. Keep Hue Behind One Adapter

`coordinator/hue.py` strictly loads the fixed protected configuration and runs
one `aiohue` V2 lifecycle on a dedicated thread beside the existing threaded
HTTP server. A bridge without the accepted HTTPS resources and event stream
fails pairing and requires reopening the Planpoint 3 input decision instead of
adding a legacy polling path.

Only sanitized room names, scene names, remote product/model, control numbers,
and advertised event names enter adapter inventory. The coordinator receives
only one operational status:

- `unconfigured` for a missing credential;
- `invalid_configuration` for malformed or identity-mismatched configuration;
- `connecting` during each connection attempt;
- `connected` after resource and event connection;
- `unreachable` after a bridge request failure;
- `unauthorized` after the bridge rejects the application key; and
- `event_interrupted` while the V2 event stream reconnects.

`GET /api/health` includes that status as `hue`. It continues returning
coordinator status `ok`; Music snapshots, endpoint actions, and the HTTP server
do not depend on Hue availability.

### 4. Recover Without Hidden State

Restart the adapter while retaining the credential:

```sh
ssh <server-ssh-host> 'sudo systemctl restart cortex-home.service'
```

Restart or power-cycle the bridge normally, wait for it to return to the LAN,
and inspect only the safe operational state:

```sh
curl --fail-with-body http://<server-host>:8080/api/health
```

It should pass through an unavailable or interrupted state and return to
`connected` without another link-button press.

If the bridge deliberately rejects or removes the application registration,
delete only the fixed invalid credential and pair again:

```sh
ssh -t <server-ssh-host> \
  'sudo rm /etc/cortex-home/hue.json && sudo systemctl restart cortex-home.service'
./coordinator/pair-hue <server-ssh-host> <bridge-host>
```

The removal is intentional and irreversible; it does not delete Hue scenes,
remote mappings, or other applications.

## Problems Encountered

### 1. Automatic `aiohue` Discovery Is Not Local-Only

- Symptom: The maintained library's hostless N-UPnP helper contacts a Philips
  discovery service.
- Diagnosis: `aiohue` can validate and characterize a known bridge entirely on
  the LAN, but does not include mDNS discovery.
- Resolution: Accept the bridge host only as a validated runtime argument and
  call the library's local `discover_bridge(host)` path. Do not add Zeroconf or
  use the cloud helper.
- Remaining caveat: The operator obtains the bridge's local hostname or address
  from the router, mDNS, or Hue app before running the repository command.

### 2. Local Systemd Verification Needs The Installed Environment

- Symptom: `systemd-analyze verify` on the development machine reports that
  `/opt/cortex-home/venv/bin/python` does not exist.
- Diagnosis: The unit deliberately targets the isolated interpreter created by
  the server installer, not the development machine's system Python.
- Resolution: Verify the unit on the deployed server after the installer has
  created the environment.
- Remaining caveat: None once deployment and remote verification complete.

### 3. Deployment And Pairing Require Reviewer Sudo

- Symptom: The existing server SSH account reaches the host through a key but
  prompts interactively before changing `/opt`, `/etc`, or systemd.
- Diagnosis: The host intentionally has no passwordless administrative
  deployment path.
- Resolution: Keep both repository commands behind interactive `sudo`; the
  reviewer enters the password directly at each prompt.
- Remaining caveat: Automated work can prepare and inspect the commands but
  cannot supply the reviewer credential.

### 4. Hue V1 And V2 Expose Different Bridge-ID Shapes

- Symptom: The first physical authorization connected to the expected bridge
  but stopped before storing its application key with `The connected bridge
  identity changed`.
- Diagnosis: Local discovery returns `aiohue`'s normalized 12-character bridge
  identity, while the authenticated V2 bridge resource retains the equivalent
  16-character form containing its inserted middle marker. Direct string
  comparison incorrectly treated the two representations as different.
- Resolution: Normalize the authenticated V2 identity with `aiohue` before
  comparing it with discovery or protected configuration.
- Remaining caveat: The failed first attempt created one unusable Cortex Home
  bridge authorization whose application key was never stored. It grants no
  access without that discarded key and may be removed later through the
  bridge's application cleanup UI if it is listed.

## Heatmap

## Hot

### H1 - Install One Library, Not One Platform

- Decision: Pin `aiohue==4.8.1` as the only direct Python dependency in an
  isolated coordinator environment.
- Where: `coordinator/requirements.txt`, `coordinator/install-host`, and
  `coordinator/files/cortex-home.service`.
- Why: It is the maintained Hue boundary already used by Home Assistant and
  supplies authentication, HTTPS resources, and V2 events without adding Home
  Assistant's runtime, configuration model, database, UI, or lifecycle.
- Alternatives: Home Assistant Container; raw Hue protocol code; system Python
  installation; vendored packages.

### H2 - Keep One Explicit Host Pairing Path

- Decision: Require a runtime bridge host and a physical-button confirmation,
  then create one protected fixed credential exactly once.
- Where: `coordinator/pair-hue` and `coordinator/hue_pair.py`.
- Why: Local validation remains cloud-free and pairing remains rare,
  deliberate, reviewable, and outside the browser.
- Alternatives: Philips cloud discovery; a Zeroconf dependency; browser
  onboarding; committed or repeatedly printed keys.

### H3 - Contain Async Hue State In One Adapter

- Decision: Run one dedicated adapter thread and publish only one safe
  operational status to the existing coordinator.
- Where: `coordinator/hue.py` and `coordinator/cortex_home.py`.
- Why: Hue failure must not block the synchronous HTTP server, but one device
  does not justify an async rewrite, adapter registry, or separate service.
- Alternatives: Rewrite around an async framework; generic provider
  abstraction; separate Hue daemon.

### H4 - Preserve Bridge Ownership

- Decision: Read inventory and events but do not create, mutate, or delete
  scenes, remotes, mappings, lights, or other clients.
- Where: `coordinator/hue.py` and the pairing flow.
- Why: Cortex Home remains a replaceable bridge client, so taking it down does
  not make the room difficult to control.
- Alternatives: Move existing Hue configuration into Cortex Home or make the
  coordinator the exclusive lamp-control path.
