# LGT-002: Control The Warm Room Scene

Previous identifier: `GH-009`.

## What

- Bound one coordinator-owned room action to the exact Hue room `Rum` and its
  `Warm` scene without exposing bridge resource identifiers.
- Added a bounded adapter operation that recalls `Warm` and completes only
  after a later Hue scene event reports it active.
- Added normalized `room.lighting` snapshots with only `scene`, `status`, and
  `observedAt`.
- Added allow-listed `room.scene.activate` requests with distinct unavailable,
  timeout, and command-failure results.
- Kept scene actions independent of endpoint availability while serializing all
  visible room interactions.
- Added persistent Warm state and temporary action feedback to the existing
  Music display without adding a lighting control.
- Added one dependency-free operator command that checks safe health and
  observed Warm completion on the deployed system.

## Implementation Walkthrough

### 1. Resolve And Observe One Exact Hue Target

`coordinator/hue.py` owns the fixed product names `Rum` and `Warm`. After the V2
bridge initializes, it requires exactly one room with that name and exactly one
scene with that name whose Hue group is the matched room. Zero or multiple
matches leave lighting unavailable. The adapter never selects the first
provider resource or exports the matched IDs.

The scene controller normalizes Hue's static or dynamic active values to
`active`; every other observed target-scene value becomes `inactive`. A missing
target or interrupted event connection becomes `unavailable`.

The adapter subscribes before issuing a recall. `HueSceneControl` registers a
new observation waiter, calls `aiohue`'s scene recall on the adapter event loop,
and completes only when a later target-scene event reports active. One timeout
covers both the bridge request and observation wait. The adapter translates:

- no usable target or a lost event connection to scene unavailable;
- no matching event before the bound to scene timeout; and
- a rejected recall request to scene failure.

The existing `/etc/cortex-home/hue.json` credential format and pairing command
do not change. GH-009 needs no new secret, migration, or link-button press.

### 2. Publish Lighting And Execute One Semantic Action

`coordinator/cortex_home.py` owns this exact snapshot:

```json
{
  "scene": "Warm",
  "status": "active",
  "observedAt": "2026-07-26T12:00:00.000Z"
}
```

`status` is only `active`, `inactive`, or `unavailable`. The coordinator adds
the timestamp, stores only the latest snapshot in memory, suppresses unchanged
updates, publishes changes as `room.lighting`, and sends the current snapshot
after `music.playback` on every endpoint connection.

The existing action endpoint now allow-lists both `endpoint.identify` and
`room.scene.activate`. Invoke the scene action from any local caller:

```sh
curl \
  --fail-with-body \
  --header 'Content-Type: application/json' \
  --data '{"requestId":"warm-1","action":"room.scene.activate"}' \
  http://<server-host>:8080/api/actions
```

Every invocation needs a request ID not previously used during the current
coordinator process. The scene action accepts no additional fields and does not
require an endpoint connection. When an endpoint is connected it receives
`action.status` events for accepted and terminal state, but the coordinator and
Hue adapter execute the action.

For the focused deployed path, run:

```sh
./coordinator/verify_warm_scene.py <server-host>
```

The standard-library verifier first requires coordinator status `ok` and Hue
status `connected`, reports whether the endpoint is connected, generates a
unique request ID, and invokes the same action. It reports success only after
the coordinator returns observed completion. It prints no health payload,
network address, Hue identifier, or credential.

A completed response is:

```json
{
  "requestId": "warm-1",
  "action": "room.scene.activate",
  "status": "completed"
}
```

Terminal failures use the same request and action fields plus `status: failed`,
a safe error, and one of:

| HTTP | Code | Meaning |
|---|---|---|
| 503 | `scene_unavailable` | The target or Hue event connection is unavailable |
| 504 | `scene_timeout` | No matching active observation arrived in time |
| 502 | `scene_failed` | The bridge rejected the recall command |

Only one visible room action may be active. A second returns `action_busy`;
reused request IDs return `duplicate_request_id`. Endpoint replacement or
disconnection still fails an endpoint-owned identify request, but does not
cancel a Hue-owned scene request.

### 3. Present Persistent State And Temporary Feedback

`coordinator/client/src/music.js` keeps lighting, playback, connection, and
interaction as independent room state. Updates to any one preserve the others.

`coordinator/client/src/App.jsx` adds a non-interactive status badge:

- `Warm active` with the existing warm highlight;
- `Warm inactive` with a neutral indicator; or
- `Warm unavailable` with the existing failure color.

The existing full-screen interaction layer uses scene-specific states:

- accepted: `Warming the room.` and `Waiting for Hue to confirm the scene.`;
- completed: `Warm is active.` and `The room confirmed the scene.`; and
- failed: `Couldn’t warm the room.` followed by the coordinator's safe error.

The badge and disconnected notice occupy separate positions at narrow widths.
No button, focus target, scene picker, or browser-to-Hue path was added.

### 4. Deploy And Recover

Deploy through the unchanged stable entry point:

```sh
./coordinator/install homelab
```

The installer rebuilds the React client, copies the coordinator and Hue module,
recreates `/opt/cortex-home/venv` from `coordinator/requirements.txt`, verifies
the service, and restarts it. It preserves `/etc/cortex-home/hue.json`.

Confirm only safe operational state:

```sh
curl --fail-with-body http://<server-host>:8080/api/health
```

Hue should report `connected`. The lighting target is intentionally absent from
health and appears only in the normalized endpoint snapshot.

If target resolution after connection or restart finds a renamed or duplicate
room or scene, or finds `Warm` under another group, the action remains
unavailable. Restore one exact `Rum` → `Warm` match, then restart the
coordinator so it resolves the bridge inventory again:

```sh
ssh homelab 'sudo systemctl restart cortex-home.service'
```

If the bridge or event stream is interrupted, no restart or re-pair should be
needed. Wait at most 60 seconds after restoring the bridge for health to return
to `connected` and the lighting badge to return to an observed state.

## Problems Encountered

### 1. The First Timeout Covered Only Observation

- Symptom: Final review found that a slow Hue recall request could consume time
  before the scene observation timeout began.
- Diagnosis: The first adapter implementation bounded `await observation` but
  not the preceding `scenes.recall`.
- Resolution: Put both recall and observation inside one `asyncio.timeout`
  context and add a regression test with a deliberately slow recall.
- Remaining caveat: The synchronous thread handoff keeps a one-second safety
  margin only to detect a stuck adapter loop; the Hue coroutine itself remains
  bounded by the coordinator action timeout.

### 2. Overlay Dependency Checking Included Host Packages

- Symptom: `pip check` in a temporary `uv run --with` overlay reported that the
  development host's unrelated `urwid` installation lacked
  `typing-extensions`.
- Diagnosis: The overlay added `aiohue` to the current interpreter environment
  instead of checking only the deployment dependency set.
- Resolution: Create a fresh temporary virtual environment, install
  `coordinator/requirements.txt`, and run `uv pip check` against that
  interpreter. All 13 installed packages are compatible.
- Remaining caveat: The development host still has its unrelated package
  mismatch; it does not enter the isolated coordinator environment.

### 3. Systemd Verification Requires The Installed Interpreter

- Symptom: Local `systemd-analyze verify` reports that
  `/opt/cortex-home/venv/bin/python` is not executable.
- Diagnosis: The unit deliberately references the interpreter created by
  `coordinator/install-host`, which does not exist on the development laptop.
- Resolution: Keep local Python, shell, dependency, and repository checks
  separate and run systemd verification on the deployed server after install.
- Remaining caveat: The live systemd result is reviewer-owned and remains
  unchecked below.

### 4. No Browser Runtime Is Available In The Development Environment

- Symptom: The repository environment has no Chromium, Chrome, Playwright, or
  Puppeteer runtime for a local screenshot or interaction pass.
- Diagnosis: Frontend dependencies intentionally contain only the application
  build and unit-test tools.
- Resolution: Verify reducer behavior, formatting, and the production build
  automatically, and provide exact real-endpoint visual checks below.
- Remaining caveat: Visual, responsive, and keyboard judgments remain with the
  reviewer.

## Heatmap

## Hot

### H1 - Resolve One Product Target By Exact Hue Names

- Decision: Bind `room.scene.activate` to exactly `Rum` → `Warm`.
- Where: `coordinator/hue.py`.
- Why: Exact names preserve a semantic action without storing or publishing
  provider IDs and fail loudly after unexpected Hue configuration changes.
- Alternatives: Persist provider IDs; accept caller-supplied names or IDs;
  select the first bridge resource; add a configuration UI.

### H2 - Complete Only From A Later Scene Observation

- Decision: A successful recall response is not completion; a new target-scene
  active event is required within the total action bound.
- Where: `HueSceneControl` in `coordinator/hue.py`.
- Why: The display, physical input, and future agent need feedback based on
  observed room state rather than command acceptance.
- Alternatives: Complete from the recall response; sleep and infer success;
  poll aggregate brightness or power.

### H3 - Serialize Feedback While Keeping Action Owners Independent

- Decision: Permit one active coordinator action while allowing Hue actions to
  continue without an endpoint.
- Where: `PendingRequest` and `Coordinator` in
  `coordinator/cortex_home.py`.
- Why: One full-screen interaction layer cannot present overlapping actions,
  but the display is an observer rather than the Hue executor.
- Alternatives: Provider-specific action queues; overlapping feedback;
  endpoint-required room actions; a general scheduler.

## Stylistic

### S1 - Keep Inactive Deliberately Broad

- Choice: Present `Warm active`, `Warm inactive`, or `Warm unavailable`.
- Alternative: Infer lamp power, expose another scene name, or show individual
  lamp state.
- When to apply: Keep this wording while `Warm` is the only accepted room
  action; expand it only when another action needs more observed state.

## Notes

- Static and dynamic Hue scene activity both normalize to `active`.
- `inactive` means only that Hue does not report `Warm` active. It does not
  identify another scene or describe individual lamp power.
- Correcting a target that was absent during initial bridge connection requires
  restarting `cortex-home.service` so inventory is resolved again.
- The existing protected Hue credential and manual Hue controls remain
  unchanged.
