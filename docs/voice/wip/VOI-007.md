# VOI-007: Stream Active-Session Dialogue

# What

- **Status: complete** - The dialogue, streaming, cancellation, and failed-child
  paths are implemented, covered, and approved for completion.
- **One dialogue per session** - Keep one coordinator-owned Pi Agent Core child
  for all turns in an explicit voice session.
- **Short-lived memory** - Keep at most six complete exchanges and 6,000 text
  characters in memory, then discard them with the session.
- **Early speech** - Turn ordered answer text into local WAV segments and play
  the first useful segment before the provider finishes the full answer.
- **Private by default** - Keep transcripts, answers, and dialogue history out
  of the UI, diagnostics, logs, and durable state.

Before:

- Each turn starts a fresh child with no conversation history.
- The coordinator waits for one complete answer and one complete WAV before
  the browser can play anything.

After:

- `Ctrl`+`Alt`+`Space` starts an explicit session whose turns share one bounded
  in-memory dialogue.
- A follow-up can use recent exchanges from that session. A new session starts
  with no history.
- Safe punctuation or a 160-character whitespace boundary creates ordered
  speech segments. The browser plays them one at a time as they arrive.
- Session end, endpoint replacement, disconnect, cancellation, timeout, or bad
  child output stops the child, drops its history and queued speech, and cannot
  publish or play stale work.

## Out Of Scope

- Listening while the assistant is thinking or speaking, acoustic echo
  handling, and spoken barge-in. VOI-008 owns these.
- Wake words, passive capture, recordings, transcripts, durable conversation
  history, or provider-content logging.
- Agent tools, lighting or other room authority, and direct device access.
- Changing the selected provider, model, Vosk, Pocket TTS, or VOI-004 turn
  detector without measured evidence.

# Heatmap

### C1 - Bound active-session memory

- Decision: Choose the maximum conversation history sent with a new turn.
- Options: Exchange count, text-character count, or both.
- Impact if wrong: Too little history breaks follow-ups. Too much increases
  privacy exposure, memory use, and provider latency.
- Proposed choice: Keep both limits. Remove the oldest complete user/assistant
  pair until no more than six exchanges and 6,000 history characters remain.
- Why: The bound is simple to inspect and keeps enough recent context for
  ordinary follow-ups.
- Status: decided.

### H1 - Coordinator-owned dialogue lifetime

- Decision: One explicit session owns one persistent Node child.
- Proposed approach: Start it when the coordinator accepts the session and
  close it for every terminal session or child-failure path.
- Why: The browser and provider must not own session identity, cancellation,
  or history disposal.
- Alternatives: A fresh child per turn, browser-owned history, or a shared
  dialogue service.
- Review focus: Timeout, bad output, cancellation, disconnect, replacement,
  and shutdown must all close the same child and reject late events.

### H2 - Stream text into cancellable speech

- Decision: Synthesize useful text chunks in order instead of waiting for the
  complete answer.
- Proposed approach: Split on sentence punctuation or a 160-character
  whitespace boundary, synthesize serially, and bind every queued WAV to the
  current request.
- Why: Early speech improves response time without speaking tiny model deltas.
- Alternatives: One complete WAV, one WAV per provider delta, or delaying all
  speech until VOI-008.
- Review focus: Ending a request must invalidate the current audio and every
  queued segment before any later `play()` call.

# How to test

### Follow-up dialogue and early speech

- **Start** - On the IdeaPad, install the locked client dependencies, export a
  real `OPENROUTER_API_KEY`, run `./coordinator/develop`, and open
  `http://127.0.0.1:5173`.
- **Action** - Start a session with `Ctrl`+`Alt`+`Space`. Ask a question whose
  answer has several sentences, then ask a follow-up that depends on the first
  answer. End the session, start another, and repeat only the follow-up.
- **Expected** - The first useful sentence begins playing before the full
  provider answer completes. Segments play once and in order. The follow-up
  works in the first session; the new session has no earlier context. No spoken
  text appears in the page, diagnostics, logs, or durable files.

### Cancellation and recovery

- **Start** - Use an answer long enough to queue at least two speech segments.
- **Action** - End the session or press `Escape` while the first segment is
  playing. Repeat once while the provider is still responding, then reconnect
  the endpoint and start a fresh session.
- **Expected** - Current audio stops, queued audio never starts, the provider
  child exits, and no old event changes the replacement session. The fresh
  session can complete a normal turn.

### Failure cleanup

- **Start** - Run focused tests with a dialogue child that times out, closes
  early, emits malformed JSON, emits a mismatched request ID, or returns an
  invalid final answer.
- **Action** - Fail one active turn through each path, then inspect the child
  lifetime and try a fresh session.
- **Expected** - The turn and session fail without private content. The old
  child and its history are gone, no queued audio plays, and the fresh session
  starts one clean child.

### Physical room pass

- **Start** - Deploy the integrated issue branch through the normal
  coordinator and endpoint install flow, then use the iMac room endpoint.
- **Action** - Repeat the follow-up, early-speech, cancellation, reconnect, and
  fresh-session checks above with ordinary room audio.
- **Expected** - The room matches the IdeaPad behavior. Record only timing and
  pass/fail observations, never spoken content.
