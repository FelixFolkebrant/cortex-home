# GH-022: Run The Agent Core Locally

# What

- Extracted the Pi-backed, one-turn agent core from the production child so a
  caller injects either no tool or one exact tool definition and executor.
- Added a laptop-only local voice workbench using bounded `arecord` capture,
  the selected Vosk and Pocket TTS backends, a fresh local agent child, and
  `aplay` playback.
- Added one in-memory development tool. Its sole result explicitly says that
  it is simulated and that no room hardware was contacted or observed.
- Documented Arch/Hyprland-compatible prerequisites, default/device-selected
  ALSA use, the selected Vosk-model setup, the one local runner command, and
  manual qualification steps.

# Acceptance Criteria

- [x] One documented command starts a deliberate local voice interaction on a
  Linux development laptop without starting or contacting Cortex Home services
  or room hardware.
- [x] The local input boundary records one bounded utterance from an explicitly
  selected or documented default input and always releases the device on
  completion, cancellation, and failure.
- [x] The selected Vosk backend transcribes the existing 16 kHz mono PCM shape,
  the pinned OpenRouter route runs the turn, and the selected Pocket TTS backend
  produces audio for the local output boundary.
- [x] One turn can either answer without a tool or request exactly one
  allow-listed development tool, receive its bounded sanitized result, and
  produce the final spoken answer in the same Pi turn.
- [x] Tool definitions and execution are injected into the agent turn; the core
  does not import the development tool, coordinator, Hue adapter, audio device,
  or deployment configuration.
- [x] Unknown, malformed, repeated, parallel, stale, or cancelled tool requests
  fail without a second execution, and the development tool result cannot be

  completed, failed, and cancelled phases without printing or persisting audio,
  transcripts, answers, tool arguments, tool results, or provider content.
- [x] `Ctrl`+`C` and bounded component timeouts release local audio resources,
  abort unfinished model work where supported, and ignore late results.
- [x] Missing audio commands or devices, invalid PCM, unavailable models,

  synthesis failure, and playback failure each produce an explicit terminal
  error.
- [x] Automated tests exercise answer-only, successful tool continuation,

- [ ] A manual IdeaPad pass confirms one spoken answer, one spoken tool-backed

- [x] Agent, Python, production dependency, audit, syntax, and whitespace checks

# Plan Diff

- None. The runner uses ALSA's standard `arecord` and `aplay` commands, which
  select PipeWire's ALSA compatibility default on an ordinary Arch/Hyprland
  laptop and allow an explicit ALSA device name when needed.

# Implementation Walkthrough

1. `coordinator/agent/agent-turn.js` owns request bounds, a fresh Pi Agent Core
   instance, the pinned caller-provided provider payload lock, and exact
   zero-or-one sequential tool enforcement. It records a tool execution only
   after the injected executor starts, rejects malformed, unknown, repeated,
   parallel, cancelled, or late tool paths, and accepts only one bounded final
   plain-text answer.
2. `coordinator/agent/answer-child.js` keeps the production Today/Music prompt,
   exact context validation, empty tool list, and its existing newline JSON
   protocol. `coordinator/install` and `coordinator/install-host` copy the new
   shared core with that production child.
3. `coordinator/agent/local-agent-child.js` composes the shared core with
   `coordinator/agent/development-tool.js`. The local child accepts only the
   fixed development marker context, publishes the content-free `acting` event,
   and uses the same pinned OpenRouter model and privacy route. The development
   tool has an empty schema, performs no I/O, and returns only an explicit
   simulated result.
4. `coordinator/local_audio.py` owns the local ALSA process boundary. `arecord`
   creates only an in-memory 16 kHz mono signed-PCM WAV stream; `aplay` receives
   the synthesized WAV over standard input. Each process has a short polling
   cancellation path, a fixed timeout, process-group termination, and pipe
   closure.
5. `coordinator/local_voice.py` composes recording, Vosk transcription, the
   local child, Pocket TTS synthesis, and playback. It prints only lifecycle
   phase names and content-free terminal error codes. It creates a fresh local
   request ID for every interaction, rejects a stale child response with a
   different ID, and keeps captured audio, transcript, answer, arguments, and
   result in memory only.
6. On an Arch development laptop, follow the `Local Voice Workbench` section in
   `coordinator/README.md` to install `alsa-utils`, Node, pnpm, Python, the
   locked packages, and the checksum-verified selected Vosk model. Start one
   interaction with:

   ```sh
   OPENROUTER_API_KEY=<private-key> \
     .venv/bin/python coordinator/local_voice.py \
     --vosk-model "$HOME/.local/share/cortex-home/vosk-model-small-en-us-0.15"
   ```

   Use `arecord -L` and `aplay -L`, then pass `--input-device <alsa-name>` or
   `--output-device <alsa-name>` if PipeWire's ALSA default is not the intended
   microphone or speakers. `Ctrl`+`C` cancels the one current interaction. No
   deployment, coordinator, endpoint, Hue, iMac, Sonos, or browser command is
   involved.

# Problems Encountered

## 1. The fresh laptop lacks the local runtime prerequisites

- Symptom: `node`, `pnpm`, `arecord`, and `aplay` are not available; only
  Python 3.14 is installed.
- Diagnosis: The development laptop is a fresh Arch/Hyprland installation and
  has not yet received the voice-workbench dependencies.
- Resolution: Added an explicit, minimal Arch setup and selected-model
  verification path to `coordinator/README.md`; make Vosk's generic invalid
  model exception a content-free `speech_unavailable` terminal error; retained
  fully faux automated coverage so no package, credential, network,
  microphone, or speaker is needed for the Python checks.
- Remaining caveat: The real local voice pass still needs the documented audio,
  speech, model, and credential setup by the laptop operator.

# Heatmap

Reference: `../project/HEATMAP.md`.

## Hot

### H1 - Keep The Agent Core Independent Of Integrations

- Decision: The shared Pi turn accepts only caller-injected prompt, runtime,
  provider payload lock, one optional tool definition, and one executor.
- Where: `coordinator/agent/agent-turn.js`.
- Why: The laptop workbench proves speech and tool continuation without giving
  reasoning code access to a coordinator, room adapter, local audio device, or
  deployment configuration.
- Alternatives: Copying a local coordinator mode; allowing the agent child to
  import room integrations; creating a dynamic registry or plugin framework.

### H2 - Use A Clearly Non-Product Development Tool

- Decision: Ship exactly one in-memory, empty-schema tool whose only result is
  explicitly simulated.
- Where: `coordinator/agent/development-tool.js`.
- Why: It proves the same-turn tool continuation without producing a laptop or
  room side effect or pretending to be observed production state.
- Alternatives: Hue access, local shell/filesystem/network controls, a clock,
  arbitrary commands, or a general tool registry.
