# Implementation Walkthrough

## 1. Preserve The Observed Endpoint Baseline

The repository-owned session entry point is
`endpoint/imac/files/cortex-endpoint-session`. The live endpoint matches it:

| Boundary | Observed baseline |
|---|---|
| Operating system | Ubuntu 24.04.4 LTS, x86-64 |
| Display session | LightDM, X11 display `:0`, Openbox, 1920×1200 |
| Kiosk | Snap Chromium 150 in the session script's restart loop |
| Composition | No Picom, Compton, or xcompmgr process |
| Graphics | Kernel `radeon` driver on a Radeon HD 2600-class adapter |
| Memory | 4 GB |
| Discovery | Avahi active and listening for mDNS |
| Audio | Endpoint PulseAudio session active; repository policy selects the one built-in PCI analog sink |
| Receiver | UxPlay absent; Ubuntu candidate `1.68.2-1build2` |

The Chromium process is launched again two seconds after it exits. Closing its
window is therefore not a stable way to control the experiment. Openbox owns
the recovery-terminal and endpoint-volume chords, while the channel shortcuts
remain browser key handlers and need Chromium focus.

## 2. Use The Distribution Package For The Experiment

Ubuntu 24.04 offers UxPlay `1.68.2-1build2`. The package uses the same X11,
Avahi, GStreamer, OpenSSL, and libplist boundaries documented by upstream and
supports optional PIN pairing, fullscreen X11 output, an explicit PulseAudio
sink, and explicit video dimensions.

The upstream release considered at the start of the experiment was UxPlay
1.73.6. Building that release would require a C/C++ toolchain, `pkg-config`,
CMake 3.10 or newer, and the development packages for OpenSSL, libplist, Avahi
DNS-SD, GStreamer base, and optionally X11. Those development packages are not
installed on the endpoint and are not needed to answer GH-019, so the
experiment does not build from source.

Two temporary no-root probes were attempted before choosing the normal package:

1. UxPlay plus its DNS-SD compatibility library had no unresolved linked
   libraries and printed its help, but startup failed because the endpoint has
   no usable GStreamer base, good, bad, or libav plugin set.
2. A 75 MiB tree extracted from the simulated new package set still failed
   plugin discovery when libav reached a library outside the extracted runtime
   closure.

Both trees used dedicated paths below `/tmp`, advertised no receiver, and were
deleted by an exit trap. A custom package resolver would add experiment-only
machinery and is not pursued.

and snapshot the installed package set before changing it:

```sh
su - imac
dpkg-query -W -f='${db:Status-Abbrev} ${binary:Package}\n' |

```

Record the reported UxPlay version and added package names in this issue, but
do not copy the endpoint hostname, addresses, device identifiers, PIN, client
name, or raw logs.

The physical install reported UxPlay `1.68.2-1build2` and `wmctrl
1.07-7ubuntu3`. The first startup then failed before advertisement because
Ubuntu's UxPlay dependency set did not restore the GStreamer base, good, bad,
X11, or PulseAudio plugin packages. Installing those five explicit runtime
groups produced an initial delta of 136 packages from the original snapshot.
The later X11 transparency probe added `xcompmgr`, `x11-utils`, and their two
previously absent libraries, bringing the exact teardown delta to 140.

Start UxPlay from the recovery terminal as the graphical
`cortex-endpoint` user so it shares the existing X11 and PulseAudio session.
Before starting, `whoami` must report `cortex-endpoint`, not the administrator
account:

```sh
whoami
test ! -e /tmp/cortex-gh019-uxplay-home
mkdir -m 700 /tmp/cortex-gh019-uxplay-home
HOME=/tmp/cortex-gh019-uxplay-home \
  uxplay \
  -n 'Cortex AirPlay Experiment' \
  -nh \
  -pin \
  -fs \
  -s 1920x1200 \
  -as pulsesink
```

Do not redirect UxPlay output to a file. Keep the recovery terminal visible
only long enough to read the random PIN and content-free failures. Use
`Control`+`C` in that terminal to stop the receiver.

## 4. Exercise Receiver And Window Recovery

With UxPlay running:

1. Open iPhone Control Center, select Screen Mirroring, select
   `Cortex AirPlay Experiment`, and enter the terminal PIN.
2. Record whether discovery, pairing, first moving image, stop, and reconnect
   succeed. Record only behavior and elapsed time, never mirrored content.
3. Observe whether the receiver is fullscreen and borderless and whether it
   initially opens above Chromium.
4. Press the existing channel and recovery-terminal shortcuts. Record which
   actions still work with UxPlay focused and whether focus can return to
   Chromium without terminating the mirror.
5. In a second recovery terminal, run `wmctrl -l -x` to identify the UxPlay and
   Chromium windows. Lower the receiver beneath Chromium with:

   ```sh
   wmctrl -r '<observed UxPlay window title>' -b add,below
   ```

6. Confirm the opaque Chromium baseline completely hides the lower receiver
   and that Today, Music, Camera, shared room feedback, and their normal
   keyboard behavior still work.

The lower-window title is deliberately observed at runtime rather than assumed
or stored as endpoint configuration.

The live GStreamer window reported the exact class
`Cortex AirPlay Experiment.GStreamer`, but published PID `0`; its initial
1918×884 geometry left visible native framing despite UxPlay's `-fs` option.
PID-based `wmctrl` selection therefore matched nothing. Selecting the exact
class, adding Openbox `fullscreen` and `below` states, then adding `above` to
`chromium.Chromium` removed the receiver framing, made its window borderless
and fullscreen, and made Chromium the only visible window while the active
mirror continued underneath.

The first transparency attempt used `xcompmgr -a`. That server-side debugging
mode kept Chromium opaque. Restarting the temporary compositor with
`xcompmgr -c -C`, its documented client-side translucency mode, and setting
Chromium's `_NET_WM_WINDOW_OPACITY` property to `3221225471` rendered the whole
Chromium window at 75% opacity. The active UxPlay mirror then remained visible
beneath Chromium.

With Chromium raised and focused through `wmctrl`, the existing Today and Music
shortcuts, channel presentation, and shared feedback remained usable over the
active mirror. Stopping and restarting the iPhone mirror succeeded, but UxPlay
created a fresh GStreamer window above Chromium. Interrupting and relaunching
UxPlay, then reconnecting the iPhone, also succeeded. Each new GStreamer window
started above Chromium and did not inherit the previous fullscreen/below state,
so production recovery cannot rely on a one-time `wmctrl` command or stable X11
window ID.

The working temporary composition command, run as `cortex-endpoint`, was:

```sh
xcompmgr -c -C &
sleep 1

wmctrl -x \
  -r 'Cortex AirPlay Experiment.GStreamer' \
  -b add,fullscreen,below
wmctrl -x -r 'chromium.Chromium' -b add,above
wmctrl -x -a 'chromium.Chromium'

chromium_id=$(
  wmctrl -lx |
    awk '$3 == "chromium.Chromium" { print $1; exit }'
)

xprop \
  -id "$chromium_id" \
  -f _NET_WM_WINDOW_OPACITY 32c \
  -set _NET_WM_WINDOW_OPACITY 3221225471
```

Reapply the two UxPlay/Chromium `wmctrl` commands after every mirror start
because GStreamer creates a new native window.

## 5. Keep Measurements Content-Free And Bounded

Before mirroring and while it is active, run these from a recovery terminal.
Each sampling window is ten seconds:

```sh
pactl get-default-sink
pactl list short sink-inputs
uxplay_pid=$(pgrep -n uxplay)
timeout 10 top -b -d 1 -p "$uxplay_pid"
```

Record the default sink name only as “the built-in PCI analog sink,” whether a
UxPlay sink input appears there, approximate UxPlay CPU and resident memory,
visible frame drops or tearing, and whether the Sonos line-in plays mirror
audio. Do not record audio, screen content, sink-input metadata, addresses, or
device identity. Stop each diagnostic immediately if it exceeds 60 seconds.

The first active mirror used UxPlay as `cortex-endpoint` with the exact launch
command above. The iPhone discovered the named receiver, completed random-PIN
pairing, displayed a working full-screen mirror, and played audio through the
room speaker through the Sonos line-in. The default remained the built-in PCI
analog sink, and UxPlay created a PulseAudio sink input on that route. A
ten-second moving-mirror sample observed approximately 16–56% UxPlay CPU,
87–90 MiB resident memory, no swap use, and roughly 3.0 GiB available system
memory. Visual graphics quality was reported as working well.

A second ten-second sample covered the relatively static layered composition:
UxPlay used approximately 132 MiB resident memory, Chromium 292 MiB, and
`xcompmgr` 8 MiB. The sampled processes used 0–2% CPU, the system used no swap,
and approximately 2.9 GiB remained available.

## 6. Recommendation And Follow-Up Scope

Pursue the layered Chromium approach in a separate implementation issue. The
real endpoint proved that UxPlay can receive the iPhone mirror and audio, that
Openbox can keep its native GStreamer window below Chromium, and that
client-side X11 composition can reveal it through a translucent Chromium
window while existing channel controls and feedback remain usable.

The smallest credible follow-up is one deliberate AirPlay vertical slice:

1. Add an endpoint-owned lifecycle helper that starts and stops UxPlay and the
   accepted compositor, keeps pairing output out of persistent logs, observes
   every GStreamer window creation, and reapplies fullscreen/below state.
2. Give the coordinator a narrow AirPlay status contract containing only
   unavailable, ready-with-ephemeral-PIN, mirroring, and failed states. It must
   contain no client identity, mirrored content, raw receiver output, or
   retained pairing secret.
3. Add one explicit AirPlay channel and fixed shortcut. Its view shows pairing
   guidance and the current ephemeral PIN, uses the qualified Chromium opacity
   while active, and keeps shared room feedback and channel controls visible.
4. Restore fully opaque Chromium, stop native receiver/compositor processes,
   and restore the room audio route on every channel exit, receiver failure,
   coordinator disconnect, kiosk restart, and endpoint-session shutdown.

Do not add a general native-window framework, casting abstraction, recording,
remote access, audio-only mode, or permanent pairing registry in that issue.
The implementation must decide how the helper consumes the random PIN from
UxPlay without exposing it in process arguments or durable logs.

## 7. Restore The Kiosk After Every Physical Run

As `cortex-endpoint`, restore opaque Chromium, remove its temporary window
state, and stop the experiment processes:

```sh
chromium_id=$(
  wmctrl -lx |
    awk '$3 == "chromium.Chromium" { print $1; exit }'
)

xprop -id "$chromium_id" -remove _NET_WM_WINDOW_OPACITY
wmctrl -x -r 'chromium.Chromium' -b remove,above
pkill -INT -x uxplay || true
pkill -x xcompmgr || true
rm -rf -- /tmp/cortex-gh019-uxplay-home
rm -f -- /tmp/cortex-gh019-xcompmgr.pid
```

Then enter the administrator account, purge exactly the packages absent from
the starting snapshot, remove the snapshot files, and restore the accepted
audio route:

```sh
su - imac
xargs -r sudo apt purge --yes -- < /tmp/cortex-gh019-packages-added
rm /tmp/cortex-gh019-packages-before
rm /tmp/cortex-gh019-packages-added
exit
/usr/local/bin/cortex-endpoint-audio-route >/dev/null
pgrep -a openbox
pgrep -a chrome | sed -n '1p'
```

The final two commands must show Openbox and the Chromium kiosk. Confirm Today,
Music, Camera, shared feedback, and the endpoint volume shortcuts behave as
they did before the run. No UxPlay process, package, temporary HOME, service,
autostart entry, compositor, or changed audio route may remain.

# Problems Encountered

## 1. A minimal unpacked UxPlay binary could not start

- Symptom: A five-second headless startup stopped before advertisement and
  reported missing GStreamer `app`, `libav`, `playback`, `autodetect`, and
  `videoparsersbad` plugins.
- Diagnosis: Package records for some GStreamer plugin sets remain on the
  endpoint, but the corresponding runtime plugins are not installed.
- Resolution: Use Ubuntu's dependency-resolved package for the physical
  experiment, then explicitly install the upstream-required GStreamer base,
  good, bad, X11, and PulseAudio runtime groups. Record every newly installed
  package for exact cleanup.
- Remaining caveat: Ubuntu's package metadata did not itself install all
  runtime plugin groups required by the executable.

## 2. Extracting the simulated new package set was not self-contained

- Symptom: A 75 MiB, 42-package temporary runtime tree still stopped before
  advertisement; its libav plugin first failed on missing `libblas.so.3`.
- Diagnosis: GStreamer plugins dynamically load a broader runtime closure than
  the simple simulated-new-package extraction captured.
- Resolution: Deleted the temporary tree and rejected a custom recursive
  package-bundling mechanism as unnecessary issue-only infrastructure.
- Remaining caveat: None; no package or endpoint configuration was changed.

## 3. UxPlay did not expose its window under its process ID

- Symptom: The first `wmctrl` lowering command completed without error, but
  UxPlay remained above Chromium with visible native framing.
- Diagnosis: GStreamer's X11 window published PID `0`, not the owning UxPlay
  process ID, and its geometry remained 1918×884 despite the `-fs` launch
  option.
- Resolution: Targeted the exact GStreamer window class and applied Openbox
  `fullscreen` plus `below` state while explicitly raising and focusing the
  Chromium class.
- Remaining caveat: Class targeting depends on the explicit experiment name;
  a production lifecycle owner would need to set and own that name.

## 4. Server-side composition did not honor window opacity

- Symptom: Chromium remained fully opaque after `xcompmgr -a` started and its
  X11 opacity property was set.
- Diagnosis: `xcompmgr -a` is automatic server-side composition intended for
  debugging; `xcompmgr` documents translucency support under client-side `-c`
  mode.
- Resolution: Restarted the temporary compositor as `xcompmgr -c -C`, restored
  the native window order, and reapplied 75% Chromium opacity.
- Remaining caveat: The successful probe makes the entire Chromium window
  translucent. A product AirPlay view must keep text and shared feedback opaque
  while revealing the mirror only through its channel surface.

# Heatmap

## Hot

### H1 - Prefer A Reproducible Distro Package To A Custom Runtime Bundle

- Decision: Use Ubuntu's UxPlay 1.68.2 package for the bounded physical test
  and capture the exact newly installed package set for teardown.
- Where: Physical experiment commands in this record.
- Why: The unpacked binary and simulated package tree both failed GStreamer
  plugin discovery, while building upstream or resolving a private runtime
  closure would add machinery unrelated to the composition decision.
- Alternatives: Build upstream 1.73.6, create a recursive unpacked bundle, or
  defer the receiver test.
- Review focus: A discovery, pairing, or decoder failure in Ubuntu's older
  package is not evidence against UxPlay 1.73.6. Test the current upstream
  release as a bounded fallback before recommending deferral when version skew
  could explain the failure.

### H2 - Stop At The Opaque Stack Until Native Layering Is Proven

- Decision: Test UxPlay below unchanged opaque Chromium before creating any
  transparent/translucent browser experiment.
- Where: Physical window-stack sequence in this record.
- Why: The endpoint has no desktop compositor, so transparency is not a
  credible product boundary unless the native z-order and Chromium focus model
  work first.
- Alternatives: Add a compositor, hide Chromium, or immediately modify the
  client.
